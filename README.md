# Feedback Intelligence Engine — LLM-Powered Customer Feedback Pipeline

A pipeline that ingests unstructured reviews/support tickets, uses an LLM for
zero-shot classification (sentiment, root cause, urgency), loads the
structured output into a SQL warehouse, and runs trend/anomaly-detection
queries that flag emerging complaint clusters — with a console-style
dashboard on top.

```
data/            → synthetic review/ticket generator
llm_tagging/      → LLM classification (real API script + offline demo runner)
warehouse/        → SQL schema, loader, trend & anomaly queries
dashboard/        → self-contained HTML dashboard (Chart.js)
```

## Pipeline stages

**1. Ingest** — `data/generate_reviews.py`
Generates 200+ synthetic reviews/tickets for a fictional SaaS product
("Nimbus"), spread over 45 days, with a deliberately injected cluster of
billing complaints in the final 3 days (simulating e.g. a botched pricing
migration). This stands in for a real feed from Zendesk/Intercom/app-store
APIs — swap the CSV output for a real pull and nothing downstream changes.

**2. Tag** — `llm_tagging/tag_reviews.py`
The real, production version: calls the Anthropic API directly (no SDK
dependency, just `urllib`) with a system prompt that defines a strict output
schema — `sentiment`, `root_cause`, `urgency`, `summary` — and validates
every response against an allowed-values set before it's accepted, falling
back to a safe default if the model returns something malformed.

```bash
export ANTHROPIC_API_KEY=sk-ant-...
cd llm_tagging
python3 tag_reviews.py --in ../data/raw_reviews.csv --out tagged_reviews.csv
```

`llm_tagging/demo_tag_offline.py` is an offline stand-in that produces
identical output shape, sourced from the synthetic dataset's ground-truth
labels instead of a live model call — useful for running the pipeline
without an API key. Swap in `tag_reviews.py` against a real key and the rest
of the pipeline is untouched.

**3. Warehouse** — `warehouse/schema.sql`, `warehouse/load_to_sqlite.py`
Two tables (`feedback`, `feedback_tags`) plus an enriched view. SQLite here
stands in for the "SQL warehouse" (Postgres/Snowflake/BigQuery in
production) — the DDL is portable with minor type changes.

**4. Detect** — `warehouse/analysis_queries.sql`
Four queries: daily volume by root cause, overall root-cause mix, a
7-day urgency-weighted "pain score" ranking, and the core anomaly
detector — a z-score of each root cause's last-48h rate against its own
trailing 30-day baseline, flagging anything above z > 2. Run against this
demo's data, it correctly catches the injected billing spike at z = 9.45.

**5. Visualize** — `dashboard/dashboard.html`
Open directly in a browser. Renders the trend chart, the anomaly alert
console, root-cause breakdown, and the actual flagged tickets — a stand-in
for a Power BI report, built with Chart.js so it's viewable without a BI
license.

## Running the whole thing end to end

```bash
cd data && python3 generate_reviews.py
cd ../llm_tagging && python3 demo_tag_offline.py   # or tag_reviews.py with a real key
cd ../warehouse && python3 load_to_sqlite.py
sqlite3 feedback.db < analysis_queries.sql          # or open feedback.db in any SQL client
open ../dashboard/dashboard.html
```

Note: `feedback.db` and `dashboard/dashboard_data.json` are generated by the
scripts above and intentionally excluded from version control (see
`.gitignore`) — regenerate them locally rather than expecting them in the repo.

## Why this approach

- **Zero-shot over regex/traditional NLP** — needs no labeled training data
  and no rule maintenance as vocabulary drifts ("double-charged" vs "billed
  twice" vs "charged again" all map to the same `root_cause` without a new
  rule).
- **48-hour anomaly window** — the anomaly query checks a rolling 48-hour
  count against a 30-day trailing baseline, so a cluster gets flagged the
  same day it starts trending instead of surfacing in a monthly report.
